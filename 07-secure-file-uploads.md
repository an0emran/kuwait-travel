# 7 - Secure File Uploads

[← Return to Chapter 6: BOLA / IDOR Remediation](06-bola-idor-remediation.md) | [Next: Security Testing →](08-security-testing.md)

---

## 7.1 Overview

The travel booking workflow permits customers to submit passport identification documents when requesting international flights, visa assistance, and religious pilgrimage packages. In the baseline prototype, file uploads were handled via an unconstrained Multer instance that lacked size restrictions, trusted client-declared metadata, and exposed files publicly on the internet.

Under **SEC-04**, the upload architecture was completely overhauled. A multi-stage validation pipeline was established enforcing strict size limits, extension whitelisting, MIME-type validation, physical magic-byte header inspection, randomized server-side filenames, and authenticated access control for stored files.

---

## 7.2 The Original Weakness

Prior to remediation, the upload handler in `server/index.js` exhibited five major vulnerabilities:

1. **No File Size Limit:** Multer accepted files of unlimited size, exposing the host server to disk exhaustion (Denial of Service).
2. **Client-Provided Extension Trust:** The filename was generated by concatenating `Date.now()` with whatever extension the client submitted (`path.extname(file.originalname)`).
3. **Absence of MIME-Type Validation:** No filter existed to verify that an uploaded payload was actually an image or document.
4. **No Magic-Byte Inspection:** An attacker could upload an executable script (`.php`, `.sh`, `.exe`, or `.html` with embedded JavaScript) simply by renaming it to `.jpg`.
5. **Publicly Accessible Storage:** Stored uploads were exposed directly via `express.static('uploads')` without authentication, allowing any unauthenticated internet crawler to enumerate and download private passport scans.

## 7.4 Formal Limits and Whitelists

The platform strictly enforces the following constraints:

### 1. Maximum File Size
- **Hard Limit:** `5 * 1024 * 1024` bytes (**5 MB**).
- Uploads exceeding this ceiling are terminated immediately by Multer and return:
  ```json
  { "error": "File size exceeds the 5MB limit" }
  ```

### 2. Permitted File Extensions
Only five safe file extensions are accepted:
- `.jpg`
- `.jpeg`
- `.png`
- `.webp`
- `.pdf`

Any other extension (e.g., `.exe`, `.sh`, `.html`, `.svg`, `.php`, `.js`, `.zip`) is rejected with `HTTP 400 Bad Request`.

### 3. Permitted MIME Types
The client-declared `Content-Type` is checked against an explicit allowlist:
- `image/jpeg`
- `image/png`
- `image/webp`
- `application/pdf`

### 4. Magic-Byte (Binary Header) Inspection
To defeat file extension spoofing (e.g., renaming a malicious script to `passport.jpg`), the server synchronously opens the newly written file and inspects the initial 16 bytes for valid cryptographic signatures:

```javascript
function validateFileSignature(filePath) {
    const buffer = Buffer.alloc(16);
    let bytesRead = 0;
    try {
        const fd = fs.openSync(filePath, 'r');
        bytesRead = fs.readSync(fd, buffer, 0, 16, 0);
        fs.closeSync(fd);
    } catch (e) {
        return { valid: false, error: 'Cannot read file' };
    }

    if (bytesRead < 4) return { valid: false, error: 'File too small' };

    // JPEG signature: FF D8 FF
    if (buffer[0] === 0xFF && buffer[1] === 0xD8 && buffer[2] === 0xFF) {
        return { valid: true, type: 'image/jpeg' };
    }
    // PNG signature: 89 50 4E 47 0D 0A 1A 0A
    if (buffer[0] === 0x89 && buffer[1] === 0x50 && buffer[2] === 0x4E && buffer[3] === 0x47) {
        return { valid: true, type: 'image/png' };
    }
    // PDF signature: %PDF- (25 50 44 46 2D)
    if (buffer[0] === 0x25 && buffer[1] === 0x50 && buffer[2] === 0x44 && buffer[3] === 0x46) {
        return { valid: true, type: 'application/pdf' };
    }
    // WebP signature: RIFF at 0..3 and WEBP at 8..11
    if (
        buffer[0] === 0x52 && buffer[1] === 0x49 && buffer[2] === 0x46 && buffer[3] === 0x46 &&
        buffer[8] === 0x57 && buffer[9] === 0x45 && buffer[10] === 0x42 && buffer[11] === 0x50
    ) {
        return { valid: true, type: 'image/webp' };
    }

    return { valid: false, error: 'Invalid file signature' };
}
```

If the signature check fails, the temporary file is unlinked immediately via `fs.unlinkSync()`, and the server returns:
```json
{ "error": "Invalid file content: file signature does not match allowed types (spoofed file rejected)" }
```

### 5. Cryptographic Random Filenames
Client-supplied filenames are completely discarded. Stored filenames are generated using the current epoch timestamp, 16 cryptographically random bytes from Node.js `crypto`, and the sanitized lowercase extension:
```javascript
const safeName = `${Date.now()}-${crypto.randomBytes(16).toString('hex')}${ext}`;
```
This guarantees that path traversal sequences (such as `../../etc/passwd` or `..\windows\system32`) cannot manipulate the file system.

### 6. Protected Upload Storage
The static file route serving the `./uploads/` directory is secured behind token authentication:
```javascript
// Remediated code in server/index.js
app.use('/uploads', verifyToken, express.static('uploads'));
```
Unauthenticated HTTP requests to `/uploads/<filename>` are rejected with `HTTP 401 Unauthorized`. Only authenticated platform users can retrieve uploaded documents.
